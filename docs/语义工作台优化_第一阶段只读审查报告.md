## 0. 执行摘要（结论先行）

1. **取数主链路已收敛为单流水线**：`POST /api/ask → agent.ask → ask_v2`（Legacy 已退役），
   三道闸门（只读 + 表权限 + 五维校验）+ 字段级/行级权限 + 唯一执行出口，fail-closed。
2. **语义中心后台与前端已存在**：前端已有「语义中心」导航组（语义工作台 / 本体建模 / 语义建模 / 逻辑视图），
   数据库已有业务域、业务主题、实体、关系、指标、维度、语义模型、本体、语义注册表等 50 张表。
3. **但存在「已建设、未接入」断层**：真正参与 SQL 生成的只有 P0~P4 直接检索链（指标/实体/关系/表字段/字典/文档/经验）；
   而**语义模型（semantic_models）默认关闭**（`SEMANTIC_MODEL_ENABLED=false`）、
   **维度表（semantic_dimensions）为空**、**本体表（ontology_*）为空**、**指标约束表（metric_constraint）派生但无消费者**。
4. **存在多处重复/冗余**（详见 §2.3）：指标口径硬约束双份存储、域/主题/模型三层映射割裂、
   实体级 JOIN 与模型级 JOIN 两套、维度三处定义、注册表与内嵌治理字段冗余。
5. **结论**：本项目不是"从零建设"，而是"**把已建成的语义中心真正接入主链路 + 治理去冗余 + 补数据**"。
   不需要新建第二套知识库/RAG/NL2SQL。

### 1.3 AI 取数链路盘点（每类知识是否真正参与 SQL 生成）

`ask_v2` 实际执行顺序与各阶段知识参与情况：

```
① enrich_index        语义索引增强（实体/关系/文档向量）
② query_understanding LLM 识别 意图/指标/实体/维度/时间
③ retrieve_semantic   P0 系统规则 → P1 指标 → P2 实体+关系 → P3 表schema → P4 文档
④ match_disabled_metric  指标权限拦截
⑤ resolve             冲突解决 + 分层 Prompt 组装（P0→P4 权威递减）
⑥ sql_experience.retrieve  历史经验检索（参考层，最后注入）
⑦ business_domain_service  业务域语义注入 ← ★ SEMANTIC_MODEL_ENABLED=false，默认空串
⑧ _build_system_prompt    role→时间口径→P0~P4→字典→硬约束→语义模型→经验
⑨ llm.chat            生成 SQL（或精确复用黄金 SQL）
⑩ _pre_execute_check  统一闸门：只读+表权限+五维校验+字段/行级权限
⑪ requirement_review  需求一致性审核（第六维，可选阻断）
⑫ _exec_sql           唯一执行出口
⑬ result_validator    结果校验 → nl_answer 自然语言回答
```

**明确参与（默认开启）**：P0 sql_rules、P1 metrics（含 required_predicates/forbidden_predicates → Validator 硬约束）、
P2 entities（主表+粒度）+ relationships（JOIN 铁律 + pre_agg_required 预聚合）、
P3 tables + table_comments + column_comments、P4 kb_docs、dict_entries、sql_experience(+rules)、同名字段硬约束。

**未参与（已建但空转/关闭）**：语义模型（开关关闭）、维度（空表）、本体（空表）、指标约束表（无消费者）、黄金 SQL（仅评测）。

## 3. 数据模型设计（复用优先，最小新增）

**总原则**：不新建第二套知识库，统一以现有 8 张知识表（entities / relationships / metrics / dict_entries /
column_comments / table_comments / kb_docs / semantic_models）为事实源，其余为派生/登记/历史表。

- **业务域**：复用 `data_domains`，补 `owner`/`department`（已有列），治理 domain_type 统一为 `business_domain`。
- **业务主题**：复用 `business_subjects`，补订单域主题；统一命名规范（英文 code）。
- **实体**：复用 `entities`，**填充** `primary_key`、`entity_code`；沿用 `grain`、`table_name`；`stable_key` 去重唯一。
- **实体关系**：复用 `relationships`，补 `from_columns/to_columns`（已有列）；沿用 `cardinality/pre_agg_required` 防一对多重复统计。
- **语义模型**：复用 `semantic_models`（model_json 为完整模型），`semantic_model_tables`/`semantic_model_joins` 为结构化明细（当前为空，需填充）。
- **指标**：复用 `metrics`，**结构化 `expression`**（分子/分母 SQL 片段，已有列），保留 required/forbidden_predicates 为 Validator 消费的单一事实源。
- **维度**：复用 `semantic_dimensions`（当前空表），定义好 `dimension_type/entity_key/source_table/source_column/model_key` 后落库，并**接入链路**。
- **逻辑视图**：第一阶段用 `semantic_models.model_json` 承载逻辑配置，不建 ClickHouse 物理 View（符合规格书要求）。

## 6. NL2SQL 接入方案（本项目最重要验收部分）

3. **本体接入**：`ontology_attributes`（实体主键/关联键）接入 P2 实体注入与 JOIN 校验，`ontology_rules` 接入 Validator。

5. **可追溯**：每个 `query_records` 增加 `trace_json`（已有列），记录本次命中的实体/关系/指标/语义模型/维度。
6. **不确定拒答**：沿用 `_refusal_reason` + 校验闸门 fail-closed，禁止编造物理表/字段/Join。

## 9. 风险清单与验收标准

### 9.1 风险清单

1. **口径漂移风险**：语义模型块与 P0~P4 直接检索两条知识来源并存，若冲突仲裁不当会静默答错（已有 S 系列整改先例）。
2. **一对多 Join 重复统计**：已用 `pre_agg_required` 治理，但模型级 `semantic_model_joins` 若落地需同步继承，否则两套 Join 口径不一致。
3. **数据源不可达 / 元数据缺失**：必须禁止编造物理表字段（沿用 fail-closed + 拒答）。
4. **存量知识质量**：49 条 column_comments 仍 candidate、3 条 rejected、实体重名，治理前接入会污染取数。
5. **开关默认关闭**：`SEMANTIC_MODEL_ENABLED` 默认 false 是"安全但无效"，上线需显式开启并灰度。
6. **改动回归**：`config_store.py`/`agent.py`/`semantic_layer.py` 高度耦合，改动需配合 test_gate/test_retrieve 回归。

### 9.2 验收标准（核心）

> 不以"页面完成 / 表创建 / 接口返回成功"为完成标准，以**实际业务问题取数准确率提升**为准。

- 业务域、实体、关系、语义模型、指标、维度**真实参与 AI 理解与 SQL 生成**（可用 `trace_json` 证明）。
- 用统一评测集（`evaluation/` + `golden_cases`）量化：业务域识别 / 实体识别 / 表字段选择 / 指标口径 / Join / SQL 执行成功 / 业务结果 / 无依据生成 / 拒答 九项准确率，改造前后对比。
- 消融实验证明 Semantic Layer / 语义模型 / Join 基数 / Validator 各自贡献。
