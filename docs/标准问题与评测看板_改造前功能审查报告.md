# 知数AI｜标准问题与评测看板 改造前功能审查报告

> 审查日期：2026-11-03
> 审查范围：标准问题模块、评测看板模块，及其依赖的 Golden SQL、评测报告、反馈、SQL 经验、知识治理。
> 审查方式：直接阅读源码（非截图推断），并核对数据库真实数据。

---

## 一、结论速览

| 模块 | 现状定位 | 后端能力 | 前端能力 | 数据现状 |
|---|---|---|---|---|
| 标准问题 | 已存在（`tab-golden`「标准问题集」） | **完整**（CRUD/审核/验证/归档/版本/导入/安全验证） | 简陋（`prompt()`/`alert()` 弹窗式操作，英文枚举直接暴露） | **空表（0 条）** |
| 评测看板 | 已存在（`tab-dash`「P0 核心指标看板」） | 聚合已存在（`/api/dashboard/p0`） | 简版（4 张卡，英文指标名裸露，无错误归因/失败详情/筛选） | 有真实数据（query_records 219 条等） |

**核心结论**：两个模块的后端能力基本齐备，本任务书要求的能力缺口主要在**前端交互与中文呈现**，以及**评测报告的「中文指标映射 + 统一错误分类」这一层展示逻辑**。真正的后端增量很小，可以不改动任何数据库结构、不覆盖任何既有数据来完成 P0。

### 2.3 状态枚举核对

| 维度 | 后端枚举值 | 任务书要求 | 是否匹配 |
|---|---|---|---|
| 状态 status | `active` / `archived` / `disabled` | 启用中 / 已归档 / 已停用 | ✅ 完全一致（仅需中文映射） |
| 审核态 review_status | `draft` / `pending` / `approved` / `rejected` | （任务书未直接定义审核态，属既有能力） | ✅ 保留 |
| 验证状态 verify_status | `unverified` / `verified` | 已验证 / 待验证 / 验证失败 / 未验证 | ⚠️ **仅 2 值，缺「待验证」「验证失败」** |

> **差异点 D1**：任务书 §3.1 要求验证状态 4 值（已验证/待验证/验证失败/未验证），后端 `golden_cases.verify_status` 仅 `unverified/verified` 2 值。
> **处理建议**：不改数据库枚举（避免破坏既有数据语义与 `sql_experience` 的另一套 5 值 `VERIFY_STATUS_ZH` 体系）。前端按「后端实际值 + 缺失值」渲染：`verified→已验证`、`unverified→未验证`；「待验证」「验证失败」作为筛选项展示但当前数据源为空，并在页面说明。若后续确需，再走迁移脚本扩充枚举（本任务 P1 之前不做，避免擅自改库）。

### 2.5 前端现状问题（P0 需修）

1. **英文枚举直接暴露**：列表用 `${esc(st)}` 直接输出 `active/archived/disabled`、`draft/pending/approved/rejected`、`unverified/verified`。
2. **弹窗式交互**：新增用连续 4 次 `prompt()`，查看详情用 `alert()` —— 无法编辑、无法复制 SQL、无法看验证记录/版本历史。
3. **筛选不足**：仅「状态」「审核态」两个下拉，缺关键词搜索、业务主题、关联指标、验证状态、创建时间。
4. **列表字段不足**：任务书 §3.2 建议的问题名称/标准问题/业务主题/关联指标/是否绑 SQL/验证状态/使用次数/最近验证时间/状态/操作，当前只拼了「问题+业务线」「审核」「验证」「结果」4 列。
5. **无统计卡片、无空状态引导**。

### 3.4 评测报告结构（`evaluation/reports/*.json`）

- 顶层：`experiment_id / tag / generated_at / dataset / metrics / results`
- `metrics`：18 个指标（**英文 key**）+ `sample_count / executed_count / api_error_count / _valid`
- `results`：每条含 `id / question / sql / error / scores`，`scores` 是 13 个评分维度（`ok/abstain/tables/metrics/forbidden/sql_contains/sql_not_contains/time/result/format/grounding/hallucination/intent`），每维度 `status ∈ {true,false,null}`。

### 3.5 前端现状问题（P0 需修）

1. 页内标题「P0 核心指标看板」—— 非产品化命名，应改为「AI取数质量中心」。
2. **AI 评测指标英文裸露**：`_latest_eval_summary` 从 markdown 反解析出英文指标名，前端 `cardRow(k, m[k])` 直接显示英文 key（如 `Overall Accuracy`、`Hallucination Rate`）。
3. **内部字段裸露**：报告的错误分布维度是 `ok / time / sql_contains / abstain` 等内部键，前端若展示会直接暴露。
4. 无时间范围筛选、评测版本筛选、评测集筛选。
5. 无错误归因分析、失败案例详情、反馈与持续优化区块。
6. 无指标悬停解释、口径说明、数据更新时间。

## 四、关键差异与处理建议（重要）

| 编号 | 差异 | 处理建议 |
|---|---|---|
| D1 | `golden_cases.verify_status` 仅 2 值，缺「待验证/验证失败」 | 不改库；前端映射现有 2 值，缺失状态作筛选项空态展示（见 2.3） |
| D2 | **`golden_cases` 表为空（0 条）** | 严格按「数据真实性优先」：列表与看板中 golden 相关指标展示**空状态/N-A**，不得填模拟数据；页面提供「新增标准问题」「从 SQL 经验沉淀」引导 |
| D3 | **标准问题（golden_cases）与 Golden SQL（sql_experience.trust_level）是两套独立体系，当前无关联字段** | 任务书 §3.5 的「标准问题→验证→Golden 候选→审核→正式 Golden」联动属 **P1**。本轮不强行加外键；看板中明确区分「正式 Golden SQL / 黄金候选 / 普通案例」（数据来自 `sql_experience.trust_level`，与标准问题库并列展示） |
| D4 | 评测报告指标为英文 key，`_latest_eval_summary` 从 md 反解析（脆弱） | 新增结构化接口直接读 JSON 报告，并在后端/前端做**中文指标名映射 + 口径说明**；错误维度映射到 12 类统一错误分类 |
| D5 | 评测错误维度是内部键（`ok/time/...`），任务书 §4.5 要求 12 类统一分类 | 建立「评分维度 → 12 类」映射表；无法映射的维度（如 JOIN、权限、字段选择在当前逐题 scores 无直接来源）归「其他问题」或显示「暂无数据」，不得编造 |
| D6 | 「业务运行数据」与「AI 评测数据」需区分 | 看板分区块 + 明确标注：核心运行概况来自 `query_records`（真实业务取数），AI 评测质量来自 `evaluation/reports`（离线评测集），两者口径不同、不得混算 |

## 六、改造影响分析

1. **零数据库迁移**：本次 P0 不新增表、不改列、不改枚举，仅新增**只读聚合接口**。风险极低。
2. **前端重构范围**：`golden.js`（全量重写两个区块）、`index.html`（`tab-golden`、`tab-dash` 两个 section 重写 DOM）、`app.css`（补充样式）。均不触碰其它 10 个 JS 文件与取数主链路。
3. **后端增量范围**：仅 `server.py` 新增 1 个只读接口 + 少量映射常量（中文指标名、维度→错误分类）。不改 `golden_cases.py` / `sql_experience.py` / `config_store.py` 核心逻辑。
4. **回归风险**：`golden.js` 的 `loadGoldenPage / loadDashPage` 被 `core.js switchTab` 按需调用；重写需保持这两个函数名与签名不变，即可保证其它页面不受影响。
