# 知数AI 语义中心重构 · 第一步：现状只读审查报告

> 审查日期：2026-11-16
> 审查方式：只读（未改动任何代码 / 数据）
> 覆盖范围：前端页面、后端 API、SQLite 表结构、知识资产映射
> 结论先行：**现有系统已具备统一语义层的完整骨架，重构是「复用骨架 + 补维度 + 重组信息架构」，不是推倒重建。**

## 一、架构总览

```
浏览器（原生 JS 单页应用）
   └─ frontend/index.html（1580 行，单页 + 15 个 JS 模块 + app.css）
          │  HTTP / SSE
          ▼
后端 API 层（FastAPI）
   └─ server.py（5014 行，186 个路由）—— 只做路由/参数校验/JSON 序列化
          │
          ▼
Agent 编排层（核心链路，不重建）
   ├─ agent.py（1287 行）—— 取数主流程编排（ask_v2 / ask stream）
   ├─ rag.py（724 行）—— 表/指标/实体/文档多路检索
   ├─ semantic_layer.py（590 行）—— P0~P4 分层 + 冲突解决 + 检索编排
   ├─ semantic_object_builder.py（613 行）—— 7 张知识表 → OSSIE 对象动态组装
   ├─ ossie_adapter.py（755 行）—— OSSIE 结构校验 / YAML-JSON 序列化
   ├─ business_domain_service.py —— 业务域识别 + 语义对象注入 Prompt
   └─ guard / sql_validator / permission / requirement_review —— 六维安全闸门
          │
          ▼
存储层
   ├─ SQLite（agent_config.db）—— 配置库 + 全部语义知识资产
   └─ ClickHouse —— 业务数据（只读账号，Schema 运行时抓取不落库）
```

**关键结论：** 项目是一个 Python/FastAPI + 原生 JS 的技术栈，没有前端框架。方案第十节「适配现有项目的技术栈，不随意引入新的大型前端框架」与现状一致，应继续沿用原生 JS + CSS。

**关键结论：** 后端 API 已经覆盖了方案各阶段所需能力的 70% 以上。方案所需的「语义工作台 / 本体建模 / 语义建模 / 逻辑视图 / AI 智能建模」五类页面，后端**大部分数据接口已存在**，缺的主要是：
1. **本体建模**三栏布局所需的「实体属性/规则/动作」结构化接口（现有只有 entities/relationships 平铺接口）。
2. **逻辑视图**所需的血缘/上下游/引用关系查询接口（现只有语义对象组装，无血缘图 API）。
3. **语义建模**所需的「表级 Join 画布」「维度管理」接口（现有关系是实体级，维度散落在 column_comments.dimension_type）。
4. **AI 智能建模**的自然语言→实体/指标/关系生成接口（现有 ai_ingest 只做口径分类落库，不做整链建模）。

### 4.3 指标类型现状

- **原子指标** = 无 `depends_metrics` 的指标

## 五、关键结论与缺口清单

### 5.1 不需要重建的（直接复用）

1. **P0~P4 语义层**、冲突解决、多路检索 —— 完全复用。
2. **治理字段规范**（status/source/stable_key/version/knowledge_level）—— 完全复用，作为所有新增语义资产的统一元数据。
3. **业务域/业务主题两层组织**（data_domains + business_subjects + topic_assets）—— 复用为「语义工作台」的数据基础。
4. **语义对象组装**（semantic_object_builder）—— 复用为「逻辑视图」「语义建模」的数据派生源。
5. **审核流 / 权限 / 六维闸门** —— 完全复用，AI 生成内容继续走 `candidate → 人工复核 → approved`。
6. **取数链路**（ask_v2 / stream / 澄清 / SQL 校验 / 执行）—— 完全不动。

### 5.2 需要补的（对照方案八大阶段）

| 缺口 | 方案对应阶段 | 落地方式 |
|---|---|---|
| 「业务域」页面缺「数据概览 + 快捷入口 + 搜索 + 发布状态」 | 阶段二 | 增强 domain.js，非新建 |
| 本体建模三栏布局（Object/Attribute/Relation/Rule/Action） | 阶段三 | 新增页面 + 复用 entities/relationships + 新增属性/规则关联表 |
| 语义建模「关系模型/指标/维度」三 Tab | 阶段四 | 复用 semantic_object_builder + 新增表级 Join 与维度表 |
| 逻辑视图（血缘/上下游/引用/冲突） | 阶段五 | 新增只读血缘 API，不新增存储 |
| AI 智能建模三入口（NL 描述/导入历史/专业模式） | 阶段六 | 增强 ai_ingest + 新增建模编排 |
| 表级 Join 显式化（主表/关联表/基数/粒度） | 阶段四 | 新增 `semantic_model_joins` 或从 relationships 派生 |
| 维度独立成表 | 阶段四 | 新增 `semantic_dimensions` |
| 统一发布记录（semantic_publications） | 阶段八 | 复用 semantic_models.status + 新增发布日志 |

### 5.3 一句话总结

> 现有系统已经是一个「有统一治理字段、有 P0~P4 分层、有 OSSIE 语义对象、有业务域/主题组织、有发布审核流」的语义平台。本次重构的本质是：**① 重组前端信息架构（平铺 15 Tab → 5 组分层导航）② 补齐本体/维度/表级 Join 三个建模能力 ③ 新增逻辑视图血缘分析 ④ 把 AI 建模与取数链路显式打通**。全程复用现有存储与治理规范，不建第二套语义存储，不动取数链路。
