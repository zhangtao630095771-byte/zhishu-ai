> 时间：2026-11-17　依据：第一阶段只读审查报告
> 设计原则：**复用现有 8 张知识事实源表，不新建第二套知识库/RAG/NL2SQL；改动以"填充 + 增强字段 + 接入链路"为主。**

## 0. 设计总纲

**目标架构**（在现有 `ask_v2` 单流水线上增强，不改主框架）：

```
业务域(data_domains) → 业务主题(business_subjects) → 语义模型(semantic_models)
        │                        │                          │
        └── topic_assets ────────┴── 实体(entities) ── 实体关系(relationships)
                                              │                  │
                                   指标(metrics) + 维度(semantic_dimensions) + 本体(ontology_*)
                                              │
                                       语义对象注入(Prompt)
                                              │
用户问题 → 查询理解 → P0~P4 检索 + 语义模型注入 → SQL生成 → 五维校验 → 权限 → 执行 → 结果解释
```

**复用 / 增强 / 新增总表**：

| 类别 | 表 | 动作 |
|---|---|---|
| 事实源（复用） | `entities` `relationships` `metrics` `dict_entries` `column_comments` `table_comments` `kb_docs` `semantic_models` | 保留 + 增强字段 + 填充 |
| 治理（复用） | `knowledge_history` `audit_log` `feedbacks` `semantic_registry` | 保留 |
| 业务组织（复用） | `data_domains` `business_subjects` `topic_assets` | 治理命名 + 补数据 |
| 结构化明细（复用） | `semantic_model_tables` `semantic_model_joins` `semantic_model_versions` `semantic_dimensions` | 从 model_json 派生填充 |
| 本体（复用） | `ontology_attributes` `ontology_rules` | 落库 + 接入链路 |
| 待收敛（去冗余） | `metric_constraint` | 与 `metrics` 内嵌约束二选一（建议删） |
| 新增（最小） | `ai_policy_drafts`（已存在 0 行） | 复用为 AI 建模方案草稿 |

## 3. AI 建模助手（统一工作流）

### 3.1 工作流（复用 ai_ingest + 新增三段式）

```
读取现有资产 → 检查数据源 → 查重复用 → 生成建模方案(草稿) → 展示差异 → 人工确认 → 执行 → 回读验证 → 审核发布
```

| 步骤 | 复用能力 | 新增 |
|---|---|---|
| 读取现有资产 | `config_store.get_*` | — |
| 检查数据源 | `db` / `rag.build_index`（真实 schema） | 数据源可达性检查 |
| 查重复用 | `stable_key` / `content_hash` | 实体同表重名检测 |
| 生成建模方案 | `ai_ingest.ingest` / `model_scenario` | 结构化方案（域/实体/关系/指标/维度）写 `ai_policy_drafts` |
| 展示差异 | — | `GET /api/modeling/assistant/{id}` 对比"现有 vs 建议" |
| 人工确认 → 执行 | `ai_ingest.apply_item` | `POST /api/modeling/assistant/{id}/apply`（分批写草稿） |
| 回读验证 | `semantic_object_builder.build_*` | 回读校验映射合法性 |
| 审核发布 | `config_store.set_knowledge_status` | 沿用现有审核流 |

### 3.2 硬约束（严格执行）

1. AI 生成内容一律 `status=candidate`（草稿），发布必须人工 `set_knowledge_status` → approved。
2. 数据源不可达/元数据缺失时：允许生成业务概念草稿，**禁止生成物理表/字段映射**（`source` 标记为概念级，无 `table_name`/`source_column`）。
3. 差异展示必须含"新增/修改/删除/冲突"四类，冲突项需人工裁决。

## 4. 本体建模（实体管理）

### 4.1 数据模型

复用 `entities`（增强：填充 primary_key / entity_code / 物理映射）：

| 字段 | 说明 | 当前 | 动作 |
|---|---|---|---|
| name | 实体名 | ✅ | 去重（同表重名收敛） |
| table_name | 落地主表 | ✅ | 保留 |
| grain | 粒度（一行=一个什么） | ✅ | 补全缺失 |
| primary_key | 业务主键 | ❌ 空 | **填充**（如 order_no / driver / customer_id） |
| entity_code | 实体编码 | ❌ 空 | **填充**（如 ENT_VALET_ORDER） |
| keywords | 别名/同义词 | ✅ | 保留 |
| comment | 业务描述 | ✅ | 保留 |
| knowledge_level / status / version / stable_key | 治理 | ✅ | 保留 |
| 物理映射（一对多） | 实体↔多表 | 仅 table_name 单主表 | 用 `ontology_attributes`(attr_type=column) 承载多表字段映射 |

**实体↔物理表支持一对多**：主表用 `entities.table_name`；卫星表/多表映射用 `ontology_attributes`（attr_key = `table.column`）或 `semantic_model_tables`（role=related/satellite）。

| 字段 | 说明 | 接入点 |

| attr_type | column / dict / derived | — |
| attr_key | column 用 `table.column`，dict 用 name | — |
| is_key | 是否主键/关联键 | 接入 P2 实体注入 + JOIN 校验 |
| label | 业务名 | 接入 P3 schema 描述 |

## 5. 实体关系管理

### 5.1 数据模型（复用 + 增强字段）

复用 `relationships`，**新增 4 字段**：

| 字段 | 现有/新增 | 说明 |
|---|---|---|
| from_entity / to_entity | 现有 | 起止实体 |
| join_sql / join_type | 现有 | JOIN 片段 / 类型 |
| cardinality | 现有 | 1:1 / 1:N |
| pre_agg_required | 现有 | 1:N 时=1（强制预聚合） |
| from_columns / to_columns | 现有(空) | **填充**关联键（JSON 数组） |
| rule_note | 现有 | 业务说明 |
| **allow_auto_join** | 新增 | 是否允许自动 Join（默认 0） |
| **agg_risk** | 新增 | 聚合风险 low/medium/high（1:N 默认 high） |
| **confidence** | 新增 | 可信度（0~1 或 low/medium/high） |
| **scenario** | 新增 | 适用场景 |
| status / version / stable_key / knowledge_level | 现有 | 审核状态、版本、分级 |

### 5.2 防一对多重复统计（关键设计）

- `cardinality=1:N` → `pre_agg_required=1`，P2 注入时打「【JOIN 铁律】」标记，Validator `_check_p2` 校验右表已预聚合。
- `agg_risk` 用于结果解释：命中 high 时在回答中提示"该指标可能受一对多关联影响"。
- `allow_auto_join=0` 的关系不参与自动 Join 建议，仅人工确认后启用。

## 6. 语义建模

### 6.1 数据模型

`semantic_models`（model_json 为完整事实源，OSSIE 格式）：

```json
{
  "name": "driver_operation",
  "datasets": [{"name":"...", "source":"物理表", "fields":[{"name":"...", "expression":{"sql":"..."}, "dimension":{"is_time":true}}]}],
  "metrics": [{"name":"...", "expression":{"sql":"..."}}],
  "relationships": [{"from":"...", "to":"...", "join":{...}}],
  "filters": [], "time_field": "..."
}
```

- `semantic_model_tables`：主实体表（role=primary）+ 卫星表（related/satellite）+ 粒度，从 model_json 派生。
- `semantic_model_joins`：结构化 Join 明细，从 model_json 派生。
- `semantic_model_versions`：每次 upsert 记录版本快照（已存在）。

### 6.2 字段设计（增强）

| 模型字段 | 说明 | 映射来源 |
|---|---|---|
| name / description | 模型名 / 描述 | business_subjects |
| 主实体 / 粒度 | 主数据集 + 粒度 | entities.table_name + grain |
| 物理表映射 | datasets[].source | entities + satellite tables |
| 关联实体/关系 | relationships[] | relationships |
| 指标集合 | metrics[] | metrics（经 topic_assets 归属） |
| 维度集合 | dimensions[] | semantic_dimensions（model_key） |
| 默认过滤规则 / 时间字段 | filters[] / time_field | 人工维护 |

### 6.3 发布与接入

- `POST /api/semantic-models/{id}/status`（draft→approved→published）。
- `POST /api/semantic-models/{id}/apply`：published 模型 + `SEMANTIC_MODEL_ENABLED=true` 时生效，`business_domain_service.build_context_block` 注入 Prompt。

## 7. 指标和维度增强

### 7.1 指标（复用 metrics + 结构化 expression）

**现状**：57 指标，`metric_type` 100% 填充（amount 8 / count 27 / ratio 6 / other 16），
但 `expression` / `metric_code` / `metric_category` 填充率 **0%**，口径仍为 `definition` 纯文本。

**增强**：结构化 `expression`（复用已有列）：

| 指标字段 | 说明 | 动作 |
|---|---|---|
| name / definition | 名称 / 业务定义 | 保留 |
| **expression** | 结构化公式（分子/分母 SQL 片段 + 过滤 + 去重） | **填充** |
| **metric_code** | 指标编码 | **填充** |
| **metric_category** | 分类（用于维度适用性） | **填充** |
| metric_type | amount/count/ratio/other | ✅ 已填充 |
| required_predicates / forbidden_predicates | 口径硬约束 | 保留（Validator 消费的**唯一**事实源） |
| required_columns | 必含字段 | 保留 |
| tables | 依赖表 | 保留 |
| conflict_key | 同名冲突键 | 保留 |

**expression 结构约定**（与 OSSIE 对齐）：
```json
{"numerator": "sum(amount)", "denominator": "sum(total)", "filters": {"status": [6]}, "distinct": "order_no", "time_field": "ctime"}
```
- 比率指标必须有分子+分母；`metric_type=ratio` → Validator `_check_ratio_denominator` 校验分母非空。
- 去重规则 `distinct` → 参与 Join 预聚合判定。

### 7.2 维度（复用 semantic_dimensions + 落库）

**现状**：`semantic_dimensions` 空表（0 行），维度散落在 model_json / column_comments.dimension_type / detect_dimension 自动派生。

**增强**：收敛到 `semantic_dimensions` 为唯一事实源：

| 字段 | 说明 | 来源 |
|---|---|---|
| dimension_key / name | 编码 / 名称 | 人工 + 派生候选 |
| dimension_type | time / geo / status / type / channel / other | detect_dimension 候选 → 人工采纳 |
| entity_key | 所属实体 | entities |
| source_table / source_column | 物理映射 | 真实元数据 |
| model_key | 所属语义模型 | semantic_models |
| hierarchy | 维度层级（JSON） | 人工 |
| analyzable | 是否可分组 | 默认 1 |
| permission_scope | 权限范围 | 复用 permission |

- **候选生成**：`semantic_object_builder.detect_dimension` 从字段名/类型自动派生候选 → 前端"维度候选"列表 → 人工采纳写库。
- **接入**：维度并入语义模型块的 `dimensions`，参与"可分组维度 + 粒度检查"。

## 8. 与取数链路接入点汇总

| 模块 | 接入点 | 方式 |
|---|---|---|
| 业务域/主题 | `business_domain_service.match_subjects` | topic_assets 反查 → 选语义模型 |
| 实体（主键/粒度/编码） | `semantic_layer.resolve` P2 注入 + `ontology_attributes.is_key` | 主表+粒度+主键注入 Prompt |
| 实体关系 | P2 注入（JOIN 铁律）+ `sql_validator._check_p2` | pre_agg 预聚合校验 |
| 语义模型 | `business_domain_service.build_context_block` | 开关开启后注入语义对象段 |
| 指标 | P1 注入（MUST 口径）+ `_check_metric` 硬约束 | required/forbidden_predicates |
| 维度 | 语义模型块 dimensions + 粒度检查 | 分组可用性 |
| 本体规则 | `sql_validator` | ontology_rules 引用规则校验 |
| 知识追溯 | `query_records.trace_json` | 记录命中实体/关系/指标/模型/维度 |

**优先级铁律**（沿用现有）：P0 系统规则 > P1 指标口径 > P2 实体关系 > 语义模型（已审核）> 经验（参考）> P3 Schema > P4 文档。
语义模型块不覆盖 P0~P2 硬约束。
