## 1. 一句话概括

知数AI 是一个**单仓单体、Python 同步后端 + 原生 JS 单页前端**的企业级 AI 取数系统：  
把「中文业务问题」经过**分层语义检索 + 单次 LLM 生成 + 四道确定性闸门**，翻译成 ClickHouse SQL 并执行。

它的工程重心不在"生成"，而&#x5728;**"生成之后如何不让错误的东西被执行"**——`agent.py` 里 1032 行代码，有近一半是校验、重试、拒答和降级逻辑。

## 3. 六层架构

### 3.1 各层职责

| 层       | 主要文件（行数）                                                                                                      | 职责                                            | 边界                  |
| ------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ------------------- |
| **接入层** | `server.py`(3287)、`frontend/index.html`(1330)+`static/js/*.js`(12 个)                                          | JWT 会话、角色鉴权、126 个 API、11 个页签                  | 只做协议转换，不含业务判断       |
| **编排层** | `agent.py`(1032)                                                                                              | `ask → ask_v2 / ask_legacy`；重试、自愈、拒答、降级、trace | **唯一**的流程控制点        |
| **语义层** | `semantic_layer.py`(578)、`rag.py`(782)、`query_understanding.py`(124)、`prompt.py`(483)、`calendar_util.py`(424) | 意图识别 → P0~P4 分层检索 → 冲突消解 → Prompt 组装          | 只产出"知识上下文"，不生成 SQL  |
| **安全层** | `guard.py`(677)、`sql_validator.py`(591)、`permission.py`(859)                                                  | 只读校验、表白名单、五维业务校验、字段级/行级权限                     | **独立于**编排层，可被单测直接调用 |
| **知识层** | `config_store.py`(3918)、`sql_experience.py`(2004)、`gaps.py`(368)                                              | 指标/实体/字典/文档/ACL/权限策略/经验案例                     | 33 张表的 CRUD 全在这里    |
| **数据层** | `db.py`(168) → `db_clickhouse.py`(425) / `db_sqlite.py`(372)                                                  | 连接池、SSH 隧道、统一门面                               | 只执行，不校验             |

### 3.2 一个刻意的设计：安全层是"旁挂"的

安全层**不嵌在** `agent.py` 的流程里，而是三个可独立调用的纯函数模块。好处是 859 行的 `permission.py`、677 行的 `guard.py` 都能被单测直接喂 SQL 验证（`test_gate.py` 122 项、`test_permission.py` 无需起服务）。

代价是：**"每个执行点都必须调用闸门"靠约定，不靠编译器**。历史上已经因此出过一次事故（见 §6.2）。

## 4. 知识是怎么组织的：P0~P4 分层

这是这套系统最核心的设计，也是它区别于"直接把表结构丢给大模型"的地方。

| 层      | 内容                      | 检索方式                 | 为什么单独成层                                |
| ------ | ----------------------- | -------------------- | -------------------------------------- |
| **P0** | 系统规则（SQL 铁律）            | **全量注入，不检索**         | 通用规则，不存在"召回不到"的问题；且必须不可被覆盖             |
| **P1** | 业务指标（含 `definition` 口径） | 关键词最长匹配 → 向量 → 按实体过滤 | 指标口径是取数正确性的第一杀手，必须优先命中、最高权重            |
| **P2** | 实体 + 关系（Join 规则）        | 实体名匹配 → 关系传递         | 解决"这张表怎么连那张表"，纯靠模型猜必错                  |
| **P3** | 表 Schema（列名/注释/类型）      | 向量 + 关键词混合，ACL 过滤    | 太宽会淹没上下文（779 张表塞不进 prompt），必须收敛到 3~5 张 |
| **P4** | 文档（业务说明、FAQ、口径澄清）       | 向量检索                 | 兜底：P1~P3 覆盖不到的业务背景                     |

**P1 有一个不显眼但关键的细节**：召回指标后还要按实体过滤（`filter_metrics_by_entity`）。否则问"小板订单"，向量会把"代驾完单量(status=40)""大板完单量(state=6)"一起捞出来，模型把 status=6 和 status=40 混着写——这是口径错误的典型来源。

**分层注入顺序 = 权威性顺序**：P0 → 时间口径 → P1 → P2 → P3 → P4 → 字典 → 同名字段硬约束 → SQL经验。越靠前越不可覆盖。新增的"经验"放在最末尾，是刻意的：**经验是参考，结构上就不允许它覆盖指标定义**。

## 5. 取数流程（11 步，含真实行号）

主链路在 `agent.ask_v2()`（`agent.py:609`）。`trace` 会记录每步耗时（`_mark`）。

| #  | 步骤                     | 位置                        | 干什么                                      | 失败后果                       |
| -- | ---------------------- | ------------------------- | ---------------------------------------- | -------------------------- |
| 0  | 语义索引增强                 | :628                      | 实体/关系/文档向量入索引，结果缓存到 `index["_semantic"]` | —                          |
| 1  | Query Understanding    | :640                      | 意图 + 指标 + 实体 + 时间表达识别                    | 识别为空则后续全靠向量                |
| 2  | P0~P4 检索               | :663                      | 分层召回 + 冲突消解                              | —                          |
| 3  | **指标权限拦截**             | :667                      | 问的是未开放指标 → 直接拒                           | **拒绝**                     |
| 4  | **空召回兜底**              | :674                      | 一张表一个指标都没命中 → 拒绝                         | **拒绝**（防编造）                |
| 5  | 冲突消解 + Prompt 组装       | :680                      | role → 时间 → P0~P4                        | —                          |
| 6  | 数据字典注入                 | :695                      | 编码→中文，如"钻石会员"→`vip_level=3`              | 漏注入 = 模型瞎猜                 |
| 7  | 同名字段硬约束                | :720                      | 跨表同名字段禁止串味                               | —                          |
| 8  | SQL 经验检索               | :732                      | 成功案例参考 / 失败经验避坑 / 规则                     | 失败仅降级，不影响取数                |
| 9  | LLM 生成 SQL             | :756                      | 单次调用（`EXP_EXACT_REUSE=0` 时）              | —                          |
| 10 | **执行前唯一闸门**            | :773 / :878               | 只读 → 表白名单 → 五维校验 → 字段/行级权限               | **拦截或回灌重试**（`MAX_RETRY=3`） |
| 11 | 执行 + 脱敏 + 结果校验 + NL 回答 | :863 / :930 / :933 / :939 | `_exec_sql` → mask → 结果合理性 → 自然语言        | 执行失败触发自愈（自愈 SQL **重新过闸门**） |

### 5.1 闸门内部（`_pre_execute_check`, agent.py:525）

```
① guard.sql_guard          非只读 / 危险语句     → hard=True, 不重试，直接拒
② guard.check_tables_ex    表白名单              → hard=True, 直接拒
③ sql_validator.validate_sql_ex  五维业务校验    → hard=False, 回灌模型修正（可重试）
④ permission.evaluate      字段级 ALLOW/MASK/DENY → hard=True, 直接拒
   ④.5 apply_row_filters   行级权限 AST 改写      → 改写后【重新过 ①②④】
```

**`hard` 这个字段是整道闸门的灵魂**：安全问题不给模型第二次机会，业务口径问题才值得重试。这个区分避免了"模型被拒→改一版→绕过安全"的经典漏洞。

### 5.2 降级策略：fail-closed

`ask()`（:983）在 V2 抛异常时**默认不回退 legacy**，只有超时/连接这类瞬时故障才降级（`LEGACY_FALLBACK_MODE=whitelist`），且**生产环境强制禁止 `always`**。

原因写在注释里：legacy 校验更弱，静默回退等于把"校验失败"偷换成"不校验地执行"。这是这套系统里我最认可的一个决策——**宁可报错，不可静默降级**。

## 6. 优点

### 6.1 架构层面

| 优点                           | 证据                                                           |
| ---------------------------- | ------------------------------------------------------------ |
| **执行单出口**                    | 所有执行收口到 `_exec_sql`，`test_gate.py` 有静态检查禁止裸 `db.execute_sql` |
| **校验单闸门**                    | 首次生成、校验重试、执行失败自愈，三条路径全部走同一个 `_pre_execute_check`             |
| **fail-closed 而非 fail-open** | 表名解析失败一律拒绝（"没认出来"≠"没有表"）；V2 异常不静默降级；行级改写后重新校验                |
| **执行 SQL == 校验 SQL**         | 闸门返回 `final_sql`（含行级改写），执行用它而不是原始 `sql`，避免"校验 A 执行 B"        |
| **分层权威性**                    | P0→P4 顺序即优先级，经验/字典只能追加不能覆盖                                   |
| **安全层可单测**                   | `guard`/`permission`/`validator` 是纯函数，122 项 gate 测试不用起服务     |

### 6.2 工程层面

- **可观测性到位**：每次取数返回 `trace`（各阶段毫秒）、`validation`（校验明细）、`perm_decision`（权限判定）、`experience`（命中经验）。排障不用猜。
- **防御性注释密度极高**：`agent.py` 里大量注释在解释"为什么这么写"而非"这是什么"，且**都带着历史事故**（"这个项目已经因为两条流水线行为漂移栽过一次"）。这是真实的组织记忆。
- **测试分层清晰**：unit（纯逻辑）/ config（需配置库）/ integration（需连库）三层，`run_tests.py` 一键跑。当前 unit 15 文件 + config 3 文件全绿。
- **演练过真事故**：2026-10-19 审计发现"自愈 SQL 绕过校验可执行未授权表"等 3 个漏洞，已全部修复并补了回归测试。

### 6.3 业务层面

- **空召回即拒答**：一张表一个指标都没命中就拒绝，而不是让模型自由发挥。这条把"幻觉"挡在了源头。
- **拒答不执行**：模型说"无法回答"时，即使它同时给了一段 SQL 也**不执行**（`_refusal_reason`）。注释写得很清楚：否则用户会以为那个数字是答案。
- **口径优先于召回率**：P1 按实体过滤指标，宁可少召回，不制造口径冲突。

## 7. 缺点与风险

按"严重程度 × 修复成本"排序。前 4 条是**结构性**问题，不是 bug。

### 7.1 前端是单文件巨兽 —— 最大工程债（✅ 2026-10-29 已拆）

`frontend/index.html` **7118 行 / 357 KB**，11 个页签、全部样式、全部逻辑塞在一个文件里，无框架、无构建、无模块化。

**具体后果**：

- 无法单测。后端有 **21 个测试文件**，前端 **0 个**；
- 任何改动都是"在 7000 行里找位置插入"，本次新增经验中心就是这样加了 768 行；
- 样式靠内联 `<style>` 各页签自己写，`.xp-*`、`.trust-chip` 等前缀已经出现命名扩散；
- 首屏要下载整个 357 KB（未压缩），移动端体验差。

**这是投入产出比最高、也最难下决心改的一块。**

**已处理（当日）**：按业务域切成 `index.html`(1330 行骨架) + 2 个 CSS + 12 个 JS，
代码**逐字节未改**（四条回拼断言 + 真浏览器验证）；并新增 `test_frontend_structure.py`(23 项)，
前端测试从 0 变成 23。仍然零构建、仍然不上框架 —— 见
`docs/optimization_2026-10-29.md §6.6`。

### 7.2 后端三个上帝文件

- `config_store.py` **3918 行**：33 张表的 CRUD 全在一个文件，指标/权限/文档/会话/审计混在一起。改权限策略要翻 4000 行找位置。
- `server.py` **3287 行**：126 个接口的路由、请求体、鉴权、错误处理平铺。
- `sql_experience.py` **2004 行**：本次新增，也走了一样的老路（虽然内部做了分区注释）。

**后果**：新人上手成本高、代码评审粒度粗、合并冲突频繁。

### 7.3 两条流水线并存

`ask_v2`（企业级）与 `ask_legacy`（历史版）同时存在。虽然降级被收窄到 whitelist，但：

- `legacy` **没有 `validate_sql` 五维校验**（只有 guard + 表权限）；
- 两套 Prompt 组装逻辑（`semantic_layer.build_prompt_parts` vs `prompt.build_system_prompt`）；
- 已经出现过"v2 检索了字典却没注入、legacy 注入了"的行为漂移。

**保险丝本身也是债**：只要 legacy 还在，就得维护两套行为一致。

### 7.4 ~~存在第二条执行路径（绕过闸门）~~ ✅ 已修复

`gaps.py:92` 与 `gaps.py:115` 曾直接调用 `db.execute_sql(sql)`，**不经过 `_exec_sql`，也不经过 `_pre_execute_check`**。

**已于当天收口**：统一改走 `gaps._system_query()`（只读校验 → 真实表白名单 → `agent._exec_sql`），  
并新增全仓静态契约 `test_no_bare_exec_anywhere`——从"只守 agent.py 一个文件"升级为"扫描全仓"，  
白名单外出现裸 `db.execute_sql` 即失败。当前全仓此类调用为 **0 处**。

### 7.5 同步阻塞，没有异步与队列

`agent.ask` 全程同步，一次取数**平均 20~35 秒，P95 约 57 秒**（实测）。FastAPI 虽是异步框架，但 `llm.chat` 和 ClickHouse 查询都是阻塞调用。

**后果**：并发能力完全由 uvicorn worker 数决定；长查询会占住 worker；没有排队、没有超时熔断、没有异步回执。用户关掉页面，这次取数的算力就白烧了。

### 7.6 ~~无结果级缓存~~ ✅ 已修复

代码里曾只有两类缓存：`rag.py` 的索引缓存、`sql_experience.py` 的候选池缓存。**同一道题问两遍，会完整重跑一遍检索 + LLM 生成 + 执行 + 列中文名解析。**

**已于当天上线 `result_cache.py`**：缓存整段 payload，key 含「问题 + 用户 + 角色 + 可见表指纹 + 知识指纹 + 方言 + 模型 + 经验开关」8 项。实测重复问题 **85.6s → 0.03s**。只缓存成功结果，失败/降级不缓存；`/api/index/rebuild` 自动清空。

### 7.7 度量能力有硬缺口

94 条评测用例**全部没有 `expected_sql` / `expected_result`**。直接导致：

- `result_accuracy`（最终业务结果正确率）**永远算不出来**；
- 只能测"SQL 片段命中""表召回率"这类代理指标；
- 本次 A/B/C/D 对照因此有 5 项指标标为"暂不可测"。

**这比任何架构问题都更影响决策**——没有 ground truth，所有优化都是盲调。

### 7.8 ~~Prompt 组装分散在 4 个地方~~ ✅ 已修复

~~`semantic_layer.build_prompt_parts` + `prompt._build_dict_block` + `prompt.build_hard_constraints_block` + `sql_experience.build_prompt_block`，四段在 `ask_v2` 里靠手工顺序 `+=` 拼接。~~

**已于当天收敛为 `_build_system_prompt()` 单一函数**，返回分段清单 `parts`，并加 `PROMPT_DUMP=1` 落盘能力。顺序改由等价性测试 `test_prompt_assembly.py` 守住（把旧逻辑抄成对照组，逐字节比对）。

### 7.9 其他

| 问题            | 说明                                                                         |
| ------------- | -------------------------------------------------------------------------- |

## 8. 演进建议（按投入产出排序）

| 优先级    | 动作                                       | 为什么先做这个                  | 成本      | 状态 |

| **P0** | 给评测集补 `expected_sql` / `expected_result` | 解锁全部核心指标；不然后面所有优化都无法验证   | 中（人力标注） | 🟡 标注器已交付，待人工标 20 条 |
| **P0** | `gaps.py` 两条直连改为走 `_exec_sql`            | 消除唯一一条绕过闸门的执行路径，改动小、收益确定 | 极小      | ✅ |
| **P1** | 前端拆模块（按页签拆文件，仍零构建）                      | 7118 行单文件已到维护极限，越晚拆成本越高  | 大       | ✅ 当日完成 |
| **P1** | 给 `ask` 加结果级缓存（问题归一化 + 指标/表指纹）           | 立刻省钱、降延迟；重复问题占比通常很高      | 小       | ✅ |
| **P2** | 收敛 legacy：明确下线时间表，或至少补齐 `validate_sql`   | 消除双流水线行为漂移的根源            | 中       | 🟡 实测降级率 0%，可议下线 |
| **P2** | `config_store.py` 按域拆分（指标/权限/文档/审计）      | 降低最大文件的认知负荷              | 中       | ⬜ |
| **P3** | 引入异步任务 + 结果回执                            | 支持长查询、并发、断线重连            | 大       | ⬜ |
| **P3** | Prompt 组装收敛为单函数，可 dump 最终 prompt         | 消除"顺序靠手工"的隐性风险           | 小       | ✅ |

## 9. 一句话总结

这套系统的**安全与口径设计是超平均水准的**（单闸门、fail-closed、分层权威、拒答不执行、执行=校验），但**工程结构是长期堆叠的产物**（3900 行上帝模块、双流水线、同步阻塞）。

> 截至当天收尾，早间列出的 9 条缺点中 **4 条已修复**（第二条执行路径 / 无缓存 / Prompt 组装分散 / 前端 7118 行单文件），  
> 其余 5 条（上帝模块、双流水线、同步无异步、评测集缺 ground truth、CK 单点）仍在。

它现在的能力上限不在"能不能答对"，而在**"改得动、测得准"**：前端已经拆开（测得准仍需标注 ground truth），这两件事决定它还能往前走多远。
