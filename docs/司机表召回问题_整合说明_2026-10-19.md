## 0. 一句话问题

用户问「分组查询司机的信息费默认比例、信息费提升比例、信息费降低比例有几种搭配」，系统判定“现有表结构不足以计算”并拒答；但司机主表 `ods_tu_driver_all` 实际存在且包含其中两个比例字段。**实体召回已经命中了「司机信息表」，但这张表没有进入最终 Prompt。**

---

## 1. 系统背景（最小必要）

- 产品：知数AI，自然语言 → ClickHouse SQL 的取数助手。
- 技术栈：Python / FastAPI，单文件前端（`frontend/index.html`，内联 CSS + JS，无构建）。
- 数据源：ClickHouse（`ctc_data_warehouse`，约 753 张表；按表权限过滤后可见 30 张）。
- 知识库：SQLite（`agent_config.db`），存指标、实体、关联规则、字段注释、字典、文档。
- 流水线：

```
用户问题
 → Query Understanding（LLM 解析 metrics / entities / dimensions / time / filters）
 → P1 指标召回（关键词 + 向量，阈值 0.50）
 → P2 实体召回（关键词 + 向量，阈值 0.45）
 → P3 表召回（向量 top_k=5，再按实体做跨业务线过滤）
 → P4 文档召回
 → 组装分层 Prompt → LLM 生成 SQL → 校验 → 执行
```

关键参数（`config.py`）：

```python
TABLE_THRESHOLD = 0.45
METRIC_THRESHOLD = 0.50
TABLE_TOP_K = 5
```

拒答机制：模型输出以“无法回答”开头时，系统不执行 SQL，直接返回失败（防止“一边说答不了、一边跑出个数”）。

## 3. 数据事实核查

### 3.1 司机主表确实有比例字段

`ods_tu_driver_all`（110 个字段）中：

| 字段 | 类型 | 注释 |
|---|---|---|
| `default_information_fee_ratio` | `Nullable(Decimal(10,2))` | 信息费默认比例 |
| `activation_reduce_ratio` | `Nullable(Decimal(10,2))` | 信息费降低比例 |
| `extra_information_fee` | `Decimal(10,2)` | 司机额外服务费比例 |

其中前两个是**人工登记**的字段注释，说明知识库早就知道这两个字段；`extra_information_fee` 是库自带注释。

### 3.2 实际组合分布

按 `(default_information_fee_ratio, extra_information_fee, activation_reduce_ratio)` 分组，`is_delete=0`：

```sql
SELECT count() AS total,
       countIf(default_information_fee_ratio IS NOT NULL) AS has_default,
       countIf(activation_reduce_ratio IS NOT NULL)       AS has_reduce,
       countIf(extra_information_fee <> 0)                AS has_extra,
       uniqExact((default_information_fee_ratio,
                  extra_information_fee,
                  activation_reduce_ratio))                AS combos
FROM ods_tu_driver_all WHERE is_delete = 0;
```

结果：

```
total = 339,785
has_default = 174,176
has_reduce  = 41,242
has_extra   = 2
combos      = 24
```

出现最多的组合：

| 默认 | 额外 | 降低 | 司机数 |
|---|---|---|---|
| NULL | 0.00 | NULL | 162,846 |
| 10.00 | 0.00 | NULL | 135,688 |
| 10.00 | 0.00 | 3.00 | 36,571 |
| NULL | 0.00 | 3.00 | 2,754 |
| 10.00 | 0.00 | 5.00 | 1,108 |

**口径疑点**：`extra_information_fee` 几乎全为 0（仅 2 名司机非 0）。所以“信息费提升比例”到底是不是这个字段，需要业务确认。

### 3.3 “提升比例”在订单层另有字段

| 表 | 字段 | 注释 |
|---|---|---|
| `dwd_tu_order_all` | `information_fee_ratio` | 司机信息费百分比 |
| `dwd_tu_order_all` | `information_fee_ratio_punish` | 司机信息费处罚提升比例 |
| `ods_valet_fee_detail_all` | `raise_violation_ratio` | 提升信息费比例 |

也就是说：司机级明确的是“默认 / 降低”两个配置比例；"提升"更像是订单级的处罚结果，而不是司机静态配置。问题本身存在口径歧义。

## 4. 检索链路与代码位置

### 4.1 P2 实体召回：实际命中了

`semantic_layer.py`：

```python
ent_pool = index.get("entities") or []
ent_by_name = {e.get("name"): e for e in ent_pool}

if ent_pool and index.get("entity_vectors"):
    ents, _, _ = rag._hybrid_retrieve(
        question, ent_pool, index["entity_vectors"],

    )
    for n in ents:
        if n in ent_by_name:
            ctx.p2_entities.append(ent_by_name[n]["raw"])   # ← 存的是实体本身
            wanted_entities.add(n)
```

「司机信息表」的注册关键词包含 `["司机信息表", "司机表", "注册司机", "司机", "driver"]`，问题里含“司机”，`_hybrid_retrieve` 走**关键词精确命中**分支，直接返回它。

实测：

```
实体命中: ['司机信息表'] | 关键词精确命中（长词优先）
实体向量分数: 0.5185
```

### 4.2 P3 表召回：司机表排第 9，被 top5 截断

`rag.py` 建索引时，表的 embedding 文本只有表名 + 表注释，**字段注释不参与向量**：

```python
tables.append({
    "name": t,
    "keywords": [t],
    "doc": f"{t}：{comment}",          # ← 只有表注释
    "columns": "\n".join(cols),        # 字段注释在这里，但不进向量
    "column_list": col_names.get(t, []),
})
```

`ods_tu_driver_all` 的表注释是：

```
司机明细表,司机的基本信息,注册明细
```

与“信息费比例”没有任何字面重合。实测 30 张可见表的向量排名：

```

2  ods_tu_large_handcart_order_fee_detail_all  0.5150
3  dwd_tu_order_cancel_all                     0.5141
4  ods_valet_driver_activation_fee_info_all    0.5125

```

`named_tables()`（用户点名表识别）也没有命中，因为表自述名是“司机明细表”，与问题无 4 字以上连续重合。

### 4.3 核心缺陷：实体主表没有并入 P3

`semantic_layer.py` 的 `SemanticContext.all_table_names()`：

```python
def all_table_names(self):
    names = list(self.p3_tables)
    for m in self.p1_metrics:
        for t in (m.get("tables") or []):
            if t not in names:
                names.append(t)
    for e in self.p2_entities:
        t = e.get("raw", {}).get("table_name")   # ← 二次解包
        if t and t not in names:
            names.append(t)
    return names
```

而 `p2_entities` 里存的实体，`table_name` 就在顶层：

```
p2 entity keys: ['name', 'table_name', 'grain', 'comment', 'keywords', 'enabled', 'source']
table_name 顶层: ods_tu_driver_all
table_name 嵌套: None
```

于是 `t = None`，司机表永远不会被合并进 `tnames`，`p3_table_objs` 也就没有它。

同文件 `resolve()` 用的是正确写法：

```python
for e in ctx.p2_entities:
    p2_lines.append(f"- 实体「{e.get('name')}」主表={e.get('table_name')} ...")
```

两处不一致，说明这是遗漏而非有意设计。

### 4.4 放大器：P1 指标噪声

问题含“信息费”，P1 向量召回了三个**金额类**指标：

- 大板信息费（依赖 `ods_tu_large_handcart_order_fee_detail_all`）
- 代驾信息费（依赖 `ods_valet_fee_detail_all`）
- 司机补缴信息费次数（依赖 `ods_offline_order_driver_location_statistical_all`、`ods_tu_pay_log_all`）

这些指标的表被并入 P3，进一步挤占了表候选位置，让模型只看到费用明细，看不到司机配置。

## 5. 复现实验（可直接运行的最小脚本）

und = {"metrics": [], "entities": [], "dimensions": [], "time_range": "", "filters": []}

## 6. 根因判断（按影响排序）

| 编号 | 根因 | 位置 | 影响 |
|---|---|---|---|
| R1 | `all_table_names()` 对 P2 实体二次解包，取不到 `table_name`，实体主表不并入 P3 | `semantic_layer.py:106` | **致命**：实体识别成功也白费 |
| R2 | 表向量 doc 只含表注释、不含字段注释；`TABLE_TOP_K=5` | `rag.py:135`、`config.py:102` | 司机表 rank 9，无法靠向量兜底 |
| R3 | Query Understanding 把比例当维度、entities 返回空；P1 金额指标挤占 P3 | `query_understanding.py`、`semantic_layer.py` | 放大器，导致 P3 全是费用明细 |
| R4 | 知识库没有“信息费三类比例”的口径文档；“提升比例”司机表无同名字段 | 知识库 | 即使召回，模型仍可能拒答或答错 |

## 8. 我倾向的处理方案（待评审）

**P0（必须）**
1. 修 `all_table_names()`，并统一 `p2_entities` 的存储形态（要么统一存 `ent_item`，要么统一存 `raw`），避免其他调用点再踩。
2. 加回归测试：凡 P2 命中实体，其 `table_name` 必须出现在 `ctx.p3_tables`。

**P1（建议）**
3. 表 embedding 文本纳入高信号字段注释（至少人工注释字段），或改为“表级召回 + 字段级二次召回”两阶段。
4. 对“金额类指标”与“配置类字段”做区分：问题问“比例/配置”时，降低金额指标权重，避免费用明细表垄断 top5。
5. `named_tables` 增加实体别名/表注释片段的匹配，不仅依赖表自述名。

**P2（口径）**
6. 补一条「信息费三类比例」知识文档，明确：
   - 默认比例 = `ods_tu_driver_all.default_information_fee_ratio`
   - 降低比例 = `ods_tu_driver_all.activation_reduce_ratio`
   - 提升比例 = ？（`extra_information_fee` 还是订单级 `information_fee_ratio_punish` / `raise_violation_ratio`）
7. 若“提升比例”确为订单级，问题应改写为“按司机统计其订单中出现过的提升比例分布”，而不是“司机的三种配置比例”。
